# Fleet Telemetry vs BLE — signal matrix

> Generated by `tools/signal-matrix/generate.py` from pinned protos. Do not edit by hand — update `tools/signal-matrix/mapping.json` and regenerate.
> Pins: Fleet Telemetry [`bd076fe14948`](https://github.com/teslamotors/fleet-telemetry/tree/bd076fe1494841707528449560c4a19d0d426da4) · vehicle-command BLE protos [`a4b43c1eff0e`](https://github.com/teslamotors/vehicle-command/tree/a4b43c1eff0e09d77deb9f2dce97031141fe8c8a)

**Scope.** Cloud side: signals defined in Tesla's Fleet Telemetry protos (`teslamotors/fleet-telemetry/protos`, the data streamed to a telemetry server and the same vehicle data the Fleet API exposes as JSON). BLE side: messages in Tesla's vehicle-command protobufs as pinned in `core/src/main/proto`, which is what this app can read locally without any cloud connection.

**The headline gap:** pack voltage/current, brick voltages, module temperatures, BMS state, and true pack capacity (`NominalFullPackEnergyKwh`) exist only in Fleet Telemetry, not in the BLE protocol. OBD/CAN is the only local alternative.

**What BLE gives instead:** SOC and range, charge limits/energy/power, charge port and schedule state, closures/security, climate, TPMS, media, software update state — and the VCSEC status domain works while the car is asleep.

## How this stays current

- A scheduled workflow (`.github/workflows/signal-matrix.yml`) refreshes the vendored Fleet Telemetry protos weekly, regenerates this document, and opens a PR when anything changes.
- New upstream signals appear under *Unreviewed upstream signals* until mapping.json is updated — that is the review queue.
- BLE protos are **not** auto-bumped: `core/src/main/proto` is pinned to `TESLA_COMMIT` and upgrades are deliberate, tested changes. The workflow reports when upstream moves ahead of the pin.
- Regenerate locally: `python tools/signal-matrix/generate.py`; verify in CI: `--check`.
